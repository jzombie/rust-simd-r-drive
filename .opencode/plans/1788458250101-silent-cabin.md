# Investigation: Slow `DataStore::open()` for Large Stores

## Root Cause Analysis

Opening a large store is slow because `DataStore::open()` (`src/storage_engine/data_store.rs:84`) performs **two full backward scans** of the entire file, both single-threaded:

### Scan 1: `recover_valid_chain` (lines 389-488)
- Walks backward from file end, validating every entry's `prev_offset` chain
- For each candidate tail offset, walks the *entire* chain backward to `prev_offset == 0`
- In the normal (non-corrupted) case, this is a single O(N) walk from tail to head
- Uses scalar `EntryMetadata::deserialize` per entry (3 `from_le_bytes` calls)

### Scan 2: `KeyIndexer::build` (`src/storage_engine/key_indexer.rs:98-124`)
- Another full O(N) backward scan of the same file
- For each entry: deserialize metadata, check `seen` HashSet, insert into HashMap
- Two hash-table lookups per unique entry (3 total hash computations)
- Single-threaded, no SIMD
- Already uses `Xxh3BuildHasher` (not SipHash) — no double-hashing issue

### Combined Effect
In the normal (non-corrupted) case, both scans walk the same `prev_offset` linked list from tail to head. Total work: ~2N scalar traversals of the same chain, each doing hash-table operations.

## Proposed Changes

### 1. Add open-time benchmark
- File: `benches/storage_benchmark.rs`
- Add `benchmark_open_time(path)` that calls `DataStore::open()` and times it
- Run after writes so it measures the realistic reload scenario
- Report cold-cache and warm-cache open times separately
- Cold cache: use platform-specific cache eviction behind `#[cfg]`:
  - macOS: `purge` command
  - Linux: write to `/proc/sys/vm/drop_caches` (requires root)
  - Other: no-op
- **If eviction fails** (non-zero exit status or command not found), print `eprintln!("WARNING: cold-cache eviction failed; results reflect warm cache")` and proceed — do NOT silently degrade
- Warm cache: time repeated opens of the same file
- Use `std::process::Command` with `.status()` and check exit code

### 2. Unify `recover_valid_chain` + `KeyIndexer::build` into a single pass
- File: `src/storage_engine/data_store.rs` (lines 84-117, 389-488)
- File: `src/storage_engine/key_indexer.rs` (lines 98-124)
- **Core insight**: In the normal case, `recover_valid_chain` already walks the entire `prev_offset` chain from tail to head. This is the same walk `KeyIndexer::build` performs. Merge them.
- **Approach**: Change `recover_valid_chain` to accept a `&mut KeyIndexer` parameter. During the inner chain walk (lines 434-477), after validating each entry, insert `(key_hash, offset)` into the index using `entry().or_insert()`. This eliminates the second pass entirely.
- **Torn-write safety**: The outer byte-by-byte scan (line 396: `cursor -= 1`) still works correctly. If a candidate tail's chain is invalid, the `KeyIndexer` built during that walk is cleared via `indexer.clear()` (reuse allocation). In practice, the first candidate (file end) is almost always valid for non-corrupted files.
- **Signature change**: Define a `RecoveryResult` struct: `struct RecoveryResult { valid_tail_offset: u64, indexer: KeyIndexer }`. Return this instead of an untyped tuple to enforce clear ownership transfer.
- **Call site update**: `DataStore::open()` (line 84) destructures `RecoveryResult` and uses `result.indexer` directly instead of calling `KeyIndexer::build` separately.

### 3. Replace dual hash-table with single HashMap using `entry()` API
- File: `src/storage_engine/key_indexer.rs`
- Currently `KeyIndexer::build` uses `HashSet<u64>` (seen) + `HashMap<u64, u64>` (index) — 2 allocations, 3 hash operations per unique entry
- Replace with a single `HashMap<u64, u64, Xxh3BuildHasher>` using `entry(key_hash).or_insert(packed)`. Since we scan backward (newest first), `or_insert` naturally keeps the first (newest) entry and ignores older versions
- This reduces per-entry cost from 3 hash ops to 1 hash op, and eliminates the `HashSet` allocation entirely
- **Capacity heuristic**: Do NOT use `file_len / 21` — this over-estimates by 3-6x for real workloads. Use `file_len as usize / 128` (assuming ~128-byte average entry size). No artificial ceiling — let system memory dictate allocation. The HashMap's built-in doubling strategy handles growth efficiently.

### 4. Hoist map allocation outside candidate retry loop
- File: `src/storage_engine/data_store.rs`
- When `recover_valid_chain` builds the index, instantiate the `KeyIndexer` (and its HashMap) **once** before the outer candidate loop
- On candidate chain failure, call `indexer.clear()` to reuse the existing heap allocation
- This avoids allocation thrashing when multiple candidate tails are tested (corrupted file scenario)
- Add a `clear()` method to `KeyIndexer` that calls `self.index.clear()`

### 5. Do NOT memoize verified offsets
- Memoization of validated offsets during candidate tail sweeps is **dropped** due to a critical correctness flaw: if `indexer.clear()` wipes indexed entries on candidate failure, but memoization short-circuits re-indexing on candidate #2, the resulting index is silently missing keys
- The corrupted-file case is rare (requires prior crash/power loss), and O(K×N) re-traversal across K candidate tails is acceptable for that scenario
- This avoids both the correctness risk and the O(N) heap allocation of a memoization `HashSet`

### 6. Do NOT parallelize the index build
- Parallelizing the `HashMap` construction via Rayon is **incorrect** for append-only logs:
  - Backward scan must be sequential (linked list traversal)
  - First-seen-wins semantics require strict ordering — parallel chunk-merge allows stale entries to overwrite newer ones
  - Pre-collecting into an intermediate `Vec` adds O(N) allocation overhead that exceeds the benefit
- The single-pass unification (change #2) is the primary performance win, not parallelism

## Files to Modify

1. `benches/storage_benchmark.rs` — add `benchmark_open_time()` with cross-platform cold/warm cache reporting and explicit eviction-failure warnings
2. `src/storage_engine/data_store.rs` — modify `recover_valid_chain` to return `RecoveryResult` struct, build index during chain walk; update `open()` to use returned index; hoist allocation outside retry loop
3. `src/storage_engine/key_indexer.rs` — add `clear()` method; simplify `build()` or remove if indexing is now done inside `recover_valid_chain`; replace `seen` HashSet + `index` HashMap with single HashMap using `entry().or_insert()`
